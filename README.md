# クレーム管理システム

クレーム・インシデントの報告、承認、通知を管理する社内システム。

> ポートフォリオ公開用のリポジトリです。実際の企業向けに開発したシステムから、会社名・ドメイン・現場一覧などの固有情報を架空のものに置き換えています。登場する社名・人名・現場名・メールアドレスはすべて架空です。

Next.js (App Router) + TypeScript + Tailwind CSS v4 + shadcn/ui ／ DB・認証・写真: Supabase

## 開発の経緯

もともとはクレーム・事故の報告を Google スプレッドシートで管理しており、報告の種類ごとにタブが分かれ、誰がいつ承認したのか、誰に連絡が届いたのかが追いにくい状態でした。これをアプリにして、報告から承認・通知までを一か所で扱えるようにすることが目的です。

## 工夫した点

### 1. 承認のルールを DB で守る
承認レベル・承認者・通知先の決定を、画面ではなく DB のトリガーと行レベルセキュリティ（RLS）で行っています。

**なぜ：** Supabase はブラウザから DB に直接アクセスする仕組みなので、画面側だけでチェックしても、通信を直接送れば権限のない操作ができてしまいます。最後の砦である DB にルールを置けば、どこから操作されても同じルールが必ず適用されます。また、ルールが一か所にまとまるので、画面と DB で判断が食い違うこともありません。

### 2. 承認が止まらない承認者の決め方
報告の種類で緊急度（Lv.1〜3）が自動的に決まり、Lv.1 はその現場を担当する支店管理者が承認します。担当者がいない現場は管理者が承認します。現場名は空白・全角半角・大文字小文字の違いを無視して照合します。

**なぜ：** 緊急度を報告者が選ぶと、人によって判断がばらつき、重大な報告が軽く扱われるおそれがあります。種類で決めれば基準が一定になります。また、現場は増えたり担当が変わったりするため、担当者がいない現場の報告が誰にも承認されないまま残らないよう、必ず誰かに届く仕組みにしました。現場名は人が手で入力するので、表記の揺れで担当者が見つからないことを防いでいます。

### 3. 確実に届く通知メール
通知を送信キューに入れ、1分ごとにまとめて送信します。失敗したメールは間隔を空けて最大5回まで再送し、同じメールが二重に届かないようにしています。「送信状況」画面で、通知ごとに誰に届いたかを確認できます。

**なぜ：** 承認の操作の中でメールを直接送ると、メールサービスの一時的な障害で承認そのものが失敗したり、メールだけが消えたりします。操作とメール送信を切り離してキューにすれば、承認は確実に保存され、メールは後から確実に届けられます。承認依頼が届かないと業務が止まるため、「届いたかどうか」を画面で確認できるようにしました。

### 4. 本番データなしで試せるテスト環境
Supabase の設定がないときは、ブラウザ内（localStorage）で動くテスト環境になります。役職の違うテスト用アカウントを切り替えて、承認や通知の流れをすぐに確かめられます。画面は同じインターフェースを通して、本番とテスト環境のどちらにもつながります。

**なぜ：** このシステムは顧客の情報を扱うため、確認やデモのために本番データを使うわけにはいきません。また、承認や通知は「誰が操作して、誰に届くか」で結果が変わるので、役職ごとのアカウントを何度も切り替えて確かめる必要がありました。

### 5. 顧客情報を守る工夫（第1版）
スプレッドシートに書き込む文字列が数式として実行されないようにしたほか、通知に顧客情報を載せない、操作ログを残す、といった対策をしました。

**なぜ：** スプレッドシートは「=」で始まる入力を数式として実行するため、悪意のある入力でシートの内容が外部に送られるおそれがありました。また、スマートフォンの通知はロック画面にも表示されるため、顧客の名前などが第三者の目に入らないようにしました。操作ログは、万が一情報が漏れたときに誰がいつ何を見たのかを確認できるようにするためです。

## 今後の予定

- **現場での運用をふまえた UI/UX の改善：** 実際に現場で使ってもらい、入力に時間がかかる箇所や分かりにくい画面を洗い出して改善していきます。
- **セキュリティの継続的な見直し：** 顧客の情報を扱うシステムなので、権限設定・データの保存期間・ログの確認などを定期的に見直し、必要な対策を追加していきます。

## 役職と承認レベル

| 承認レベル | 緊急度 | 承認者（確認者） | 対象の種類 |
| --- | --- | --- | --- |
| Lv.1 | 低 | 支店管理者（その現場の担当） | 備品紛失・破損 |
| Lv.2 | 中 | 管理者 | レジ金過不足 |
| Lv.3 | 高 | 社長 | インシデント/クレーム、車両関連 |

- 役職：社長 ＞ 管理者 ＞ 支店管理者 ＞ 一般社員
- 緊急度（= 承認レベル）は報告の種類で自動的に決まる
- 上位の役職は下位レベルも承認できる（例：社長は Lv.1〜3 すべて）
- 支店管理者は複数の現場を担当できる。Lv.1 は現場名が一致する担当の支店管理者が承認し、いなければ管理者が承認する
- 現場は自由入力（登録済みの現場は入力候補に出る）。出張は「出張買取」と入力し、住所は経緯・内容に書く

## ステータスの流れ

受付（未割当）→ 対応中（担当者あり）→ 承認待ち（担当者が承認依頼）→ 完了（承認）
承認者が差し戻すと「差し戻し」になり、担当者が再度承認依頼する。

## 通知先ルール

| タイミング | 届く相手 |
| --- | --- |
| 新規報告 | そのレベルの承認者 ＋ 担当者 |
| 承認依頼 | そのレベルの承認者 |
| 承認・差し戻し | 担当者 ＋ 登録者 |

操作した本人には届かない。「送信状況」画面で通知ごとの届いた／届かなかった社員を確認できる。

本番では同じ相手にメールも送る（Supabase Edge Function + Resend、1分ごと、失敗は自動で再送）。設定は [docs/supabase-setup.md](docs/supabase-setup.md) の「通知メール」。

ルールの実装：
- 画面（デモ）：`src/lib/domain.ts` の `approversFor` / `recipientsFor`
- DB：`supabase/migrations/20261116000000_init.sql` の `claim_approvers` / `notify`（トリガーで自動実行、RLS で権限チェック）
